# miniRAG

정부 정책 PDF 한 편으로 만든 로컬 RAG 파이프라인과 청크 크기 실험입니다.

## 만든 이유

AI Core Engineer(RAG & LLM) 면접 제안을 받고, 공고의 주요 업무인 RAG를 직접 겪어보려고 이틀 동안 만들었습니다.
완성된 서비스를 만드는 것보다 **각 단계를 직접 돌려보고, 설정을 바꿨을 때 결과가 어떻게 달라지는지 재보는 것**에 집중했습니다.

## 구조

```
PDF ─▶ 로딩 ─▶ 청킹 ─▶ 임베딩 ─▶ Chroma 저장        (src/ingest.py)
질문 ─▶ 임베딩 ─▶ top-k 검색 ─▶ 프롬프트 ─▶ LLM 답변 + 출처 페이지   (src/query.py)
```

| 파일 | 역할 |
|---|---|
| `config.py` | 청크 크기, overlap, top-k, 모델 이름, 경로 등 실험용 설정값 |
| `src/ingest.py` | PDF를 페이지 단위로 읽고, 청크로 나누고, 임베딩해서 Chroma에 저장 |
| `src/query.py` | 질문과 가까운 청크 3개를 검색하고, LLM이 출처 페이지와 함께 답변 |
| `experiments/questions.csv` | 직접 만든 질문 12개와 정답 근거 페이지 |
| `experiments/run_eval.py` | 청킹 설정별로 검색만 실행해서 Hit@3, Hit@1, MRR 계산 |
| `experiments/results.csv` | 설정 × 질문별 검색 결과 |

## 기술 선택

| 구성 | 선택 | 이유 |
|---|---|---|
| 환경 | WSL2, CPU만 사용 (GPU 없음), 메모리 10GB | 개인 노트북 |
| LLM | Ollama `qwen3:4b-instruct` | 외부 API 없이 온프레미스 환경을 가정. 8B(약 6GB)는 메모리와 CPU 속도 부담이 커서 4B 선택 |
| 임베딩 | Ollama `bge-m3` (1024차원) | 한국어를 포함한 다국어 모델. LLM과 같이 올려도 약 4.4GB |
| 청킹 | LangChain `RecursiveCharacterTextSplitter` | 문단 → 줄 → 공백 순으로 잘라 문장이 덜 끊김. 페이지별로 잘라 청크마다 페이지 번호 유지 |
| 벡터 DB | Chroma (로컬 저장) | 가볍고 설치가 쉬움. 설정별로 컬렉션을 따로 저장해 재사용 |
| 문서 | 「국민주권정부 청년정책 추진방향」 (2025.9.22, 관계부처 합동, 40쪽) | 표가 포함된 한국어 공공 문서 |

## 실행

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
ollama pull qwen3:4b-instruct && ollama pull bge-m3

python src/ingest.py                              # 인덱싱 (기본 600/100)
python src/query.py "구직촉진수당은 얼마로 확대되나요?"
python experiments/run_eval.py                    # 6개 설정 실험
```

PDF는 `data/doc.pdf`에 둡니다.

## 실험: 청크 크기와 overlap

- 질문 12개를 직접 작성했습니다. 유형은 단순 정보, 복합 조건, 절차, 의도가 모호한 질문, 표, 문서에 없는 질문입니다. 각 질문의 정답 근거 페이지는 원문에서 확인했습니다.
- 검색만 평가했습니다(LLM 호출 없음). 정답 페이지가 top-3 안에 있는지(Hit@3), 1위인지(Hit@1), 정답 순위의 역수 평균(MRR)을 쟀습니다.
- 12번은 문서에 답이 없는 질문이라 채점에서 제외했습니다(11문항).

| size / overlap | 청크 수 | 인덱싱 | Hit@3 | Hit@1 | MRR |
|---|---|---|---|---|---|
| 300 / 0    | 149 | 80초  | 11/11 | 11/11 | 1.00 |
| 300 / 100  | 180 | 113초 | 11/11 | 11/11 | 1.00 |
| 600 / 0    | 80  | 78초  | 11/11 | 11/11 | 1.00 |
| 600 / 100  | 84  | 102초 | 11/11 | 10/11 | 0.95 |
| 1000 / 0   | 52  | 81초  | 11/11 | 7/11  | 0.82 |
| 1000 / 100 | 52  | 81초  | 11/11 | 8/11  | 0.86 |

**알게 된 것**

- **Hit@3는 변별력이 없었습니다.** 문서가 40쪽이라 모든 설정이 만점이었습니다. 정답 순위(Hit@1, MRR)를 추가하자 차이가 드러났습니다.
- **청크가 클수록 정답이 1위에서 밀렸습니다.** 1000자 청크는 사실상 한 페이지가 한 청크라서 여러 정책이 섞이고 임베딩 의미가 흐려집니다. 질문과의 거리도 0.82~0.92로 더 컸습니다.
- **1000/0과 1000/100의 청크 수가 같습니다.** 페이지 단위로 먼저 나누기 때문에 1000자 이하 페이지(26개)는 통째로 한 청크가 되어 overlap이 들어갈 곳이 없습니다.
- **overlap이 항상 좋지는 않았습니다.** 600/100에서는 163자짜리 꼬리 조각 청크 때문에 Q8 정답이 2위로 밀렸습니다.
- 이 문서에서는 300~600자가 적당했습니다. 다만 11문항이라 1~2문항 차이는 우연일 수 있습니다.

## 실패 사례

| 질문 | 유형 | 무슨 일이 있었나 | 원인 |
|---|---|---|---|
| Q3 군 원격강좌 수강료 | 생성 실패 | 검색은 정답 p.17을 1위로 가져왔지만, 답이 "수강료 80%, 연 64,000원" | 같은 청크 바로 다음 항목인 'e-북 지원'의 금액을 가져다 씀. 문서에는 원격강좌 금액이 없음. 한 청크에 여러 항목이 붙어 있으면 LLM이 항목 경계를 놓침 |
| Q9 전세사기 컨설팅 (1000자) | 검색 순위 하락 | '청년 금융 컨설팅·재무상담' 페이지가 1위 | '컨설팅/상담' 단어가 겹치는 다른 주제가 이김 |
| Q2 지역 중소기업 인센티브 (1000자) | 검색 순위 하락 | '중소기업 복지' 청크가 1위 | 주제 단어가 겹침 |
| Q12 해외여행 경비 (문서에 없음) | 거절 성공, 출처 오류 | "찾을 수 없습니다"라고 맞게 답했지만 [p.28]을 붙임 | 출처를 꼭 쓰라는 프롬프트 지시와 충돌 |
| Q11 학자금 이자면제 구간 (표) | 성공 | "1~6구간" 정답 | 표는 깨졌지만 본문 문장에도 같은 내용이 있었음 |

**표 파싱**: pypdf가 표를 줄 단위 텍스트로 풀어서 셀 경계가 사라지고, '신규/확대' 라벨이 과제명에 붙었습니다(예: `▸신규온라인 오프라인...`). 본문 일부는 띄어쓰기도 사라졌습니다(예: `원하는일자리가없어서`).

## 속도 (CPU)

- 임베딩: 청크당 약 0.9~1.2초 (84청크 기준 102초)
- 검색: 약 0.4초
- 생성: 약 12~14 tok/s, 질문당 10~70초. 검색된 청크를 읽는 prefill과 모델 로딩 시간이 큼
- 처음 쓴 `qwen3:4b` 태그는 thinking 전용 체크포인트라서 `think:false`로도 생각 과정이 꺼지지 않았습니다(답변당 80~138초). `ollama show`로 확인한 뒤 `qwen3:4b-instruct`로 바꿨습니다.

## 한계와 다음에 해볼 것

- **생성 평가**: 지금은 검색만 정량 평가했습니다. 답이 근거와 일치하는지(faithfulness)도 재고 싶습니다.
- **평가셋**: 11문항에 페이지 단위 채점이라 거칩니다. 질문 수를 늘리고, 청크나 정답 문장 단위로 채점하면 더 정확합니다.
- **하이브리드 검색**: BM25 + 벡터 검색. 정책명과 숫자에 강해집니다. 한국어는 형태소 분석이 필요합니다.
- **리랭킹**: cross-encoder로 top-k를 다시 정렬하면 Q9처럼 단어만 겹치는 경우를 걸러낼 수 있습니다.
- **표 추출과 구조 기반 청킹**: 표는 따로 뽑아 마크다운으로 바꾸고, 글자 수 대신 문서 항목(▸, ○) 단위로 자르기.
- **프롬프트**: 답이 없을 때는 출처를 쓰지 않도록 수정.
